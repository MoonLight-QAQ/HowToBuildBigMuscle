# 代码审查

## 准备

1. 获取 PR 信息和改动（把 `<编号>` 换成 PR 编号）：
   ```bash
   gh pr view <编号>
   gh pr diff <编号>
   ```
2. 从 PR 描述的「关联任务」中找到 issue 编号（`Closes #12` 或 `Refs #12`），执行 `gh issue view <编号>` 确认任务的范围和负责人。PR 没有写关联任务时，把这一点列为「必须修改」。
3. 阅读该任务相关的 PRD 章节、原型页面和接口契约。

## 检查项

按以下顺序检查，越靠前越重要：

1. **功能是否正确。** 是否实现了 PRD 的要求；业务规则（状态流转、权限、金额计算）是否正确；边界情况是否处理（空列表、加载中、请求失败）。
2. **范围与锁定。** 改动是否都在任务范围内；有没有修改锁定目录或共享区域，如果有，理由是否充分。
3. **契约。** 是否遵守接口契约；修改契约是否合理，是否会影响后端。
4. **项目约定。** 是否遵守根目录和对应工程的 `AGENTS.md`：分层、ID、金额、时间、状态文案、命名。
5. **安全与隐私。** 有没有提交密钥；有没有在日志或本地存储中记录敏感信息。
6. **测试。** 业务规则是否有测试；测试是否真的在验证行为，而不只是为了覆盖率。
7. **可读性。** 命名是否清楚；有没有重复代码；复杂逻辑是否有注释。

## 输出格式

按严重程度分三类，每条都写明**文件和行号**、**问题**、**建议的改法**：

### 🔴 必须修改

不改会导致错误、违反硬规则或安全问题。

### 🟡 建议修改

不影响功能，但改了更好。

### 💬 问题

需要作者解释的地方。

最后给出结论：**可以合并**、**修改后可以合并**，或**需要较大调整**。

## 注意

- **只提出意见，不要自行修改代码，也不要批准 PR。** 是否批准，由审查人自己决定。
- 不要因为代码风格的个人偏好提出必须修改。格式由格式化工具决定。
- 不确定的地方，归入「问题」，而不是「必须修改」。
