# GitHub Project 使用指南

本指南说明我们如何用 GitHub Project 管理开发任务：每个任务是什么、在哪里看、怎么改状态、怎么和 PR 关联。

**第一次接触 GitHub Project 的人，请从头读到尾，大约 15 分钟。**

| 你是谁 | 读哪几部分 |
| --- | --- |
| 仓库管理员，要第一次搭建看板 | 全部 |
| 开发者 | 第一、三、四、五部分 |

---

## 第一部分：先理解 5 个概念

### 1. Issue：一个任务

在 GitHub 上，每个开发任务是一个 **issue**。你可以把它理解为一张任务卡片，上面写着：

- **标题**：`[W-02] 城市（示例模块）`。方括号里是任务 ID，和 `docs/tasks/admin-web.md` 中的 ID 一一对应。
- **描述**：任务内容、允许修改的范围、依赖哪些任务、参考哪些文档、完成标准。
- **负责人**（Assignees）：谁来做。
- **标签**（Labels）：`task` 表示这是开发任务；`contract`、`skeleton`、`module` 表示任务类型。
- **编号**：如 `#12`，由 GitHub 自动分配，全仓库唯一。

Issue 在仓库页面顶部的 **Issues** 标签里。

### 2. Project：放任务卡片的看板

**Project** 是一块看板，所有任务卡片都放在上面。我们的看板叫「拾澳 · 管理后台前端」。

看板和仓库是分开的：同一个 issue 既在仓库的 Issues 列表里，也在看板上，改任何一边，另一边都会同步。

### 3. 字段：卡片上的属性

看板上每张卡片都有几个**字段**，相当于表格的列：

| 字段 | 含义 | 谁来改 |
| --- | --- | --- |
| **Status** | 状态：`Todo`（待办）、`In Progress`（进行中）、`Done`（已完成） | 开始任务时你自己改；完成时自动改 |
| **Assignees** | 负责人 | 一般不改，变更分工时由负责人改 |
| **开始日期** | 计划开始的日期 | 调整计划时改 |
| **截止日期** | 计划完成的日期 | 调整计划时改 |
| **估算天数** | 预计需要的工作日 | 一般不改 |

### 4. 视图：同一批任务的不同看法

同一批任务，可以用不同的**视图**来看。我们有 4 个视图，在看板顶部切换：

| 视图 | 样子 | 适合做什么 |
| --- | --- | --- |
| **看板** | 三列：Todo、In Progress、Done | **拖动卡片改状态**；一眼看出大家都在做什么 |
| **全部任务** | 一张表格 | 一次看到所有字段；直接点击修改 |
| **路线图** | 甘特图，每个任务是一条横条 | **拖动横条调整日期**；看整体进度和延误 |
| **我的任务** | 只显示分配给你的任务 | 每天开工前看一眼 |

### 5. 自动化：不用手动改的状态

看板上设置了几条自动规则：

| 发生了什么 | 看板自动做什么 |
| --- | --- |
| 新建了一个带 `task` 标签的 issue | 自动加入看板，状态设为 `Todo` |
| 关联了这个 issue 的 PR **合并**了 | 状态自动变为 `Done` |
| issue 被关闭 | 状态自动变为 `Done` |

所以你只需要手动做一件事：**开始任务时，把卡片从 `Todo` 拖到 `In Progress`。**

## 第二部分：第一次搭建看板（管理员做一次）

只需要仓库管理员做一次。完成后，其他人直接使用即可。

### 第 1 步：给 GitHub CLI 补充 Project 权限

GitHub CLI 默认没有操作 Project 的权限，需要补充：

```bash
gh auth refresh -s project
```

终端会显示一个验证码并打开浏览器。在浏览器里输入验证码，点 **Authorize**。

确认权限已补充：

```bash
gh auth status
```

输出的 `Token scopes` 一行中，应该包含 `'project'`。

### 第 2 步：先预演，再正式执行

在仓库根目录先预演一遍。预演只会打印要做的事，**不会做任何修改**：

```bash
python3 .github/project-setup/setup_project.py --dry-run
```

确认输出没有报错后，正式执行：

```bash
python3 .github/project-setup/setup_project.py
```

脚本会依次完成 6 步，每一步都会打印结果。最后会列出看板地址和每个任务的 issue 地址。**把看板地址记下来。**

脚本做了什么、能否重复执行，见 `.github/project-setup/README.md`。

### 第 3 步：让团队成员能看到看板

看板属于个人账号，**仓库的协作者不会自动获得看板的访问权限**，需要手动添加：

1. 打开看板，点右上角的 **⋯** → **Settings**。
2. 左侧点 **Manage access**。
3. 点 **Invite collaborators**，依次搜索并添加 `RealninX` 和 `celine-hy`，权限选 **Write**。

在同一个 Settings 页面，**Visibility** 选 **Private**。仓库是公开的，但任务看板没必要公开。

### 第 4 步：创建 4 个视图

脚本创建的看板只有一个默认视图。在看板页面按下面的步骤创建 4 个视图。

**视图 1：全部任务（表格）**

1. 双击顶部默认视图的名字（通常叫 `View 1`），改名为「全部任务」。
2. 点表头最右侧的 **+**，依次勾选显示这些字段：`Assignees`、`Status`、`开始日期`、`截止日期`、`估算天数`、`Labels`。
3. 点表头的「开始日期」，选 **Sort ascending**，按开始日期排序。

**视图 2：看板**

1. 点视图名称右边的 **+ New view**，选 **Board**。
2. 改名为「看板」。
3. 确认三列分别是 `Todo`、`In Progress`、`Done`。如果列不对，点视图名旁的 **▾** → **Column by** → 选 `Status`。

**视图 3：路线图（甘特图）**

1. 点 **+ New view**，选 **Roadmap**。
2. 改名为「路线图」。
3. 点视图名旁的 **▾** → **Date fields**：**Start date** 选 `开始日期`，**Target date** 选 `截止日期`。
4. 同一菜单里 **Group by** 选 `Assignees`，每人一条泳道。
5. 右上角的缩放选 **Week**，以周为单位显示。

**视图 4：我的任务**

1. 点 **+ New view**，选 **Table**。
2. 改名为「我的任务」。
3. 在视图顶部的筛选框里输入 `assignee:@me`，回车。
4. 点视图名旁的 **▾** → **Save changes**。

每个人打开「我的任务」，看到的都是分配给自己的任务。

视图调整完后，如果视图名旁出现一个小圆点，表示有未保存的修改，点 **▾** → **Save changes** 保存，否则其他人看不到。

### 第 5 步：检查自动化规则

1. 打开看板，点右上角的 **⋯** → **Workflows**。
2. 逐个检查以下规则，确保都是 **On**：

| 规则名称 | 设置 |
| --- | --- |
| **Item added to project** | 状态设为 `Todo` |
| **Item closed** | 状态设为 `Done` |
| **Pull request merged** | 状态设为 `Done` |
| **Auto-add to project** | 仓库选 `HowToBuildBigMuscle`，筛选条件填 `is:issue label:task` |

修改规则后，点右上角的 **Save and turn on workflow**。

**Auto-add to project** 的作用：以后任何人新建一个带 `task` 标签的 issue，都会自动出现在看板上，不需要手动添加。

### 第 6 步：确认结果

- 看板的「看板」视图中，`Todo` 一列有 20 张卡片。
- 「路线图」视图中，每个任务都显示为一条横条。
- 仓库页面顶部的 **Projects** 标签里，能看到这个看板。
- 请 RealninX 和 celine-hy 打开看板地址，确认能够访问。

## 第三部分：日常使用

### 每天开工前

打开看板，切到「**我的任务**」视图，看看今天要做什么。

### 开始一个任务

1. **确认依赖已完成。** 打开任务卡片，看描述里的「依赖」。依赖的任务都在 `Done` 列，才能开始。
2. **把卡片拖到 `In Progress`。** 在「看板」视图里，把卡片从 `Todo` 拖到 `In Progress`。也可以在「全部任务」视图里点 Status 单元格，直接选择。
3. **拉分支，开始开发。** 和以前一样，从最新的 develop 拉分支，见 `CONTRIBUTING.md`。

同一时间，每个人最好只有 **1 个**任务在 `In Progress`。

### 提交 PR

**PR 描述里必须写明关联的任务**，看板才能在合并后自动更新状态：

| 情况 | PR 描述里写 | 合并后 |
| --- | --- | --- |
| 这个 PR 完成了任务 | `Closes #12` | 任务自动变为 `Done`，issue 自动关闭 |
| 任务分几个 PR 完成，这只是其中一部分 | `Refs #12` | 任务状态不变，PR 会显示在 issue 页面上 |

`#12` 换成任务 issue 的编号。编号在卡片标题旁边，或者 issue 页面的地址末尾。

PR 模板里已经预留了这一行，按提示填写即可。

**完成任务的那个 PR**，还要把任务范围内的目录加入 `docs/tasks/locked-paths.txt`，见 `docs/tasks/README.md` 的「锁定」一节。

### 任务完成

PR 合并后，任务**自动**移到 `Done`，不需要手动操作。

**不要手动把卡片拖到 `Done`。** `Done` 表示代码已经合并进 develop。手动拖动会让其他人误以为可以开始依赖它的任务。

### 计划有变化时

- **任务要延期**：在「路线图」视图里，拖动横条的右端，延长截止日期。同时在 issue 里留一条评论，说明原因。
- **任务被阻塞**：在 issue 里留评论，写明被什么阻塞、需要谁处理，并 `@` 对方。
- **要换负责人**：两人沟通后，在 issue 右侧的 Assignees 里修改，并同步修改 `docs/tasks/admin-web.md` 和 `.github/CODEOWNERS`。

### 维护任务：增加、删除、修改

看板搭建完成后，**所有任务的维护都在 GitHub 网页上进行**，不需要改脚本，也不需要改 `.github/project-setup/` 下的任何文件。

每个任务的信息只存在两个地方：

| 地方 | 存什么 | 谁来改 |
| --- | --- | --- |
| **GitHub issue 和看板** | 任务的全部内容、状态、日期、负责人 | 在网页上直接改 |
| **`docs/tasks/admin-web.md`** | 全部任务的一览表：范围、依赖、负责人 | 通过 PR 改 |

`admin-web.md` 是给人和 AI 快速浏览用的一览表，所以**任务的范围、依赖或负责人变了，两边都要改**；只是状态和日期变了，只改看板。

下面是每种情况的具体做法：

| 情况 | 在 GitHub 上做什么 | 在仓库里做什么（提 PR） |
| --- | --- | --- |
| **新增任务** | Issues → New issue → 选「开发任务」模板填写。提交后自动进入看板，再在看板上填写日期和估算 | 在 `admin-web.md` 的任务表里加一行；如果是新模块，在 `.github/CODEOWNERS` 里加上它的路径 |
| **取消任务** | ① 先在看板上打开这张卡片，点 **⋯** → **Archive**，把它从看板上移走；② 再在 issue 页面点 **Close issue** 旁的 **▾**，选 **Close as not planned** | 在 `admin-web.md` 里删掉这一行，并检查有没有其他任务依赖它 |
| **修改任务的范围或依赖** | 编辑 issue 的描述 | 同步修改 `admin-web.md` 里这一行 |
| **换负责人** | 修改 issue 右侧的 Assignees | 同步修改 `admin-web.md` 和 `.github/CODEOWNERS` |
| **调整计划日期** | 在「路线图」视图里拖动横条 | 不需要 |
| **任务太大，要拆开** | 新建几个更小的任务 issue；修改原任务的范围，或者按「取消任务」处理原任务 | 在 `admin-web.md` 里相应地增删行 |

几点注意：

- **取消任务时，要先 Archive 再关闭。** 看板设置了「issue 关闭后自动移到 Done」，如果直接关闭，被取消的任务会出现在 Done 列里，看起来像是已经完成了。
- **不要删除 issue。** 取消的任务关闭即可，保留讨论记录，以后可以查。
- **影响别人的改动，先在团队里说一声。** 比如调整了某个任务的依赖，或者推迟了别人在等的任务。

### 进入新的开发阶段时

比如管理后台完成、开始做小程序时，会有一整批新任务。这时可以用脚本批量创建：

1. 复制 `.github/project-setup/tasks-admin-web.json`，改名为 `tasks-mini.json`，填入新阶段的任务。
2. 把 `setup_project.py` 顶部的 `TASK_FILE` 改为新文件名。
3. 执行脚本。已有的任务不会受影响，只会创建新任务。
4. 新建任务清单 `docs/tasks/mini.md`。

## 第四部分：AI 如何读取任务

Claude Code 和 Codex 都可以通过 GitHub CLI 读取任务，不需要你把任务内容复制给它。

### 让 AI 开始一个任务

在 Claude Code 中这样说：

```text
开始任务 W-02（issue #12）。先读取 issue 的内容，给出计划。
```

AI 会执行 `gh issue view 12` 读取任务的内容、范围和依赖，再按 `new-module` skill 进行。

### 常用的查询命令

你自己也可以在终端里用这些命令：

```bash
# 查看所有开发任务
gh issue list --label task

# 查看分配给自己的任务
gh issue list --label task --assignee @me

# 按任务 ID 查找
gh issue list --label task --search "W-02 in:title"

# 查看某个任务的详情
gh issue view 12
```

### AI 不应该做的事

AI **只读取**任务，不修改任务：不改状态、不关闭 issue、不改负责人。这些操作由人来做。`.claude/settings.json` 中已设置，AI 执行这类命令前会先征求你的同意。

## 第五部分：常见问题

**打开看板地址显示 404**

你还没有被添加到看板的访问名单里。请管理员按第二部分第 3 步添加。

**PR 合并了，任务没有自动变成 `Done`**

检查两点：

1. PR 描述里写的是 `Closes #编号`，而不是 `Refs`，编号是否正确。
2. 看板的 Workflows 里，**Pull request merged** 规则是否为 On。

如果都没问题，手动把卡片拖到 `Done` 即可。

**不小心把 issue 关闭了**

打开 issue，点底部的 **Reopen issue**，再在看板上把状态改回正确的值。

**路线图里看不到某个任务**

这个任务没有填写开始日期或截止日期。在「全部任务」视图里补上即可。

**看板上和 `docs/tasks/admin-web.md` 里的信息不一致**

| 信息 | 以哪里为准 |
| --- | --- |
| 状态、日期 | 看板 |
| 范围、依赖 | `docs/tasks/admin-web.md` |
| 负责人 | 两边都要改，保持一致 |

**以后进入小程序阶段，要新建看板吗？**

建议在同一个看板里继续，新任务加上 `mini` 标签，用视图的筛选区分阶段。也可以复制 `tasks-admin-web.json` 改为 `tasks-mini.json`，修改脚本顶部的配置后执行。
