# 退款渠道状态：Stripe 官方定义与本项目前端

核验日期：2026-11-01。用户已要求独立展示退款进度，并尽量对齐 Stripe。本文记录方案，用户已确认渠道暂未确定，先做可替换 Mock，不表示接入或执行了真实退款。

Stripe 的退款对象是 **Refund**，官方 `status` 原始值如下；前端建议保留枚举原值，只映射显示文案。[官方 Refund 对象](https://docs.stripe.com/api/refunds/object)

| 原始值 | 建议中文显示 |
|---|---|
| `pending` | 退款处理中 |
| `requires_action` | 待补充处理 |
| `succeeded` | 退款成功（渠道确认） |
| `failed` | 退款失败 |
| `canceled` | 退款已取消 |

这些值不包含“未发起”。建议用渠道退款对象尚未创建表示未发起；若对象已存在而渠道状态为空，则显示状态待确认，避免混为未发起。`succeeded` 不显示成前端已经核验顾客银行到账，点击同意或请求被受理也不直接推导为成功。渠道结果由后端可靠同步。[官方退款处理说明](https://docs.stripe.com/refunds)

本轮契约使用 `providerRefundStatus`，与审核状态分开。旧建议名 `payoutStatus` 容易混淆：Stripe 的 Payout 表示向商户银行账户或借记卡划出资金，使用另一套状态，并非顾客退款。[官方 Payout 对象](https://docs.stripe.com/api/payouts/object)

现有团队 PRD 和字段字典写的是微信退款。用户现已确认实际渠道尚未确定，本轮仅借鉴 Stripe 枚举，契约和 Mock 保留可替换的渠道边界，不据此确定支付供应商。未来接入其他渠道时须单独记录其权威状态及映射，不能把不同渠道的原始值混为一种，也不能把本轮 Mock 当作真实支付能力。

审核后渠道结果未定的申请仍占用对应可退件数和运费额度，不能因审核状态离开 `open` 而释放。发起和结算时均校验剩余可退额；成功结果按渠道退款标识幂等入账，可靠确认失败/取消后再按规则释放，避免重叠申请导致超退。此处描述后续实现必须满足的不变量，不代表本轮已执行支付或并发集成测试。
