# 0002. develop 与 main 双分支策略

- 状态：已采纳
- 日期：2026-11-01
- 决策人：@MoonLight-QAQ

## 背景

团队 3 个人，使用 AI 编码工具协作开发。需要一套分支策略，同时满足：

- 日常开发顺畅，分支不长期存在，减少冲突。
- 代码进入「可发布」状态之前，有一层集中验证的缓冲。团队刚起步，自动化测试还不完善。
- 6 个工程各自独立发版。
- 小程序和 APP 需要经过平台审核才能上线，审核期间可能要求修改。

## 决策

| 分支 | 用途 | 接收谁的合并 | 合并方式 |
| --- | --- | --- | --- |
| `main` | 已验证、可发布的代码 | 只接收 `develop` 和 `hotfix/*` | Merge commit |
| `develop` | 日常集成，仓库的默认分支 | 所有功能分支 | Squash |
| 功能分支 | 一个任务一个分支，存在 1～3 天 | — | — |
| `hotfix/*` | 线上紧急修复，从 `main` 拉出 | — | — |
| `release/*` | 只在小程序或 APP 提交审核期间使用 | — | — |

- 发布用 tag 标记，按工程区分：`范围/v版本号`，如 `fe-web/v0.1.0`。只有管理员可以创建。
- hotfix 合进 `main` 后，必须同步回 `develop`。
- 两个分支都受保护：必须通过 PR 合并、至少 1 人审批、禁止强制推送和删除。管理员可以跳过审批，但不能绕过 PR。
- 这些设置以代码形式保存在 `../../.github/repo-settings`。

## 考虑过的其他方案

| 方案 | 没有采用的原因 |
| --- | --- |
| 纯主干开发：只有 `main`，功能分支直接合进去 | 缺少集中验证的缓冲。团队刚起步、测试不完善时风险较高 |
| 完整的 Git Flow：同时维护 main、develop、release、hotfix 多条长期分支 | 对 3 个人来说太重，大量时间会花在分支之间来回合并 |
| `develop` 合进 `main` 也用 Squash | 会切断两条分支的共同历史，导致每次发版都产生冲突 |

## 后果

**好处**

- `main` 始终等于「已验证可发布」的状态，生产环境的版本都从它打 tag。
- 功能分支用 Squash 合并，`develop` 上一个 PR 对应一个提交，撤销某个 PR 非常干净。
- 合并方式按分支区分，`develop` 合进 `main` 时保留了两条分支的关系，不会反复冲突。

**代价**

- hotfix 之后需要手动同步回 `develop`，容易遗漏。已写入 `../../CONTRIBUTING.md` 的 hotfix 流程。
- `main` 上会不断出现 `develop` 没有的合并提交，所以 `git log origin/develop..origin/main` 总会有输出，不能用来判断两条分支是否一致。**要用 `git diff --stat origin/develop origin/main` 比较内容。**
- 「`main` 只接收 `develop` 和 `hotfix/*`」这条规则，GitHub 的分支保护本身无法限制，需要通过 CI 检查实现。
