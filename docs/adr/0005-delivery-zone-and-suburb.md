# 0005. 配送大区与 suburb 字典

- 状态：已采纳
- 日期：2026-11-10
- 决策人：@MoonLight-QAQ

## 背景

PRD（`docs/prd/admin-prd.md` 第 10 节）以「区」为单位设置线下配送：店员在每个线下城市勾选可送的区，如悉尼的「内西区」「东区」。

但小程序的收货地址由 Google 地图检索得到，地图返回的是具体的 suburb（如 Leichhardt）、邮编和州，而不是「内西区」这样的片区名。按名称无法把地址匹配到区。

原设计在区上挂一份 suburb 清单（`District.suburbs`，由店员录入），但它把两类性质不同的数据混在了一起：

- **suburb 本身**：澳洲官方的地理数据，名称、邮编、州是客观事实，不应由店员手工录入。
- **运营设置**：哪些地方送、收多少运费，由店铺决定，会经常调整。

## 决策

1. **Suburb 作为只读字典**，从官方数据导入，字段为 `name`、`postcode`、`state`，`name + postcode + state` 唯一。后台不新增、不修改、不删除。字典不包含城市。
2. **配送大区（DeliveryZone）负责运营设置。** 大区是店铺自定义的运营区域，属于某个城市，有默认可送设置 `deliverable` 和可选的运费 `localFeeCents`（为空时使用全店统一配送费）。以后的阶梯运费也挂在大区上。
3. **大区成员（ZoneSuburb）关联 suburb 与大区。** 每个成员可以用 `deliverableOverride` 单独覆盖可送设置，为空时跟随大区。
   - 一个 suburb 最多属于一个大区（`SUBURB_IN_OTHER_ZONE`）。
   - suburb 的州必须与大区所属城市的州一致（`SUBURB_STATE_MISMATCH`）。
4. **大区同时圈定城市的服务范围，线下和快递都适用。** suburb 属于哪个城市，由它所在大区的城市决定；地址的 suburb 不属于当前城市的任何大区时，地址越界，返回 `PLACE_OUTSIDE`。
   - **线下订单**：未加入任何大区的 suburb 不可配送；可送和运费按大区和成员的设置计算。
   - **快递订单**：只要求地址属于本市的大区，不检查可送设置，也不使用大区运费，邮费按快递邮费和包邮门槛计算。
5. **城市增加所属州 `state`**，新增时必填，创建后不能修改。它用来校验哪些 suburb 能加入这个城市的大区。

字段和规则的完整定义见 `docs/design/admin-data-dictionary.md` 第三部分。

## 快递地址怎样判定属于本市

快递订单不检查可送设置，但仍要判断地址是否属于用户选择的城市。考虑过三种做法：

| 做法 | 结论 |
| --- | --- |
| **快递城市也用大区圈定范围**，只是不看可送设置和运费 | **采用。** 「suburb 属于哪个城市，由所在大区决定」这条规则对线下和快递都成立；同一个州有多个城市时也不会混淆；不需要新增数据 |
| 按州判定：suburb 在字典中，且州与城市一致 | 「本市」实际上被放大成了「本州」；同一个州有两个城市时（如悉尼和纽卡斯尔），无法区分地址属于哪个 |
| 沿用 `mini-prd.md` 第 4.7 节，比对地图返回的城市名 | 就是本记录「背景」中的问题：地图对 Leichhardt 这类地址不返回「Sydney」，按名称匹配不可靠 |

`mini-prd.md` 中「服务器用 `placeId` 重新向地图服务取详情、不信任前端地址」的做法保留，只是把「比对城市名」换成「按 `name + postcode + state` 匹配字典中的 suburb，再看它属于哪个城市的大区」。匹配不到或不属于本市，返回 `PLACE_OUTSIDE`。

## 为什么州和时区分开保存

城市已有 `timezone` 字段。看起来可以由州推出时区，从而省掉一个字段，但州不能唯一确定时区：

- 新南威尔士州的 Broken Hill 使用阿德莱德时间（`Australia/Broken_Hill`），而不是悉尼时间。
- 昆士兰州不实行夏令时，与相邻的新南威尔士州在夏季相差一小时。

时区直接影响送达时段和订单时间的显示，算错会造成实际的配送错误。所以两个字段分开保存：新增城市时，前端按州预填时区，由店员确认。

## 考虑过的其他方案

| 方案 | 没有采用的原因 |
| --- | --- |
| 区下挂 suburb 清单（原设计） | suburb 由店员手工录入，拼写和邮编容易出错；同一个 suburb 可能被录入到多个区，无法保证唯一；地理数据和运营设置混在一起，无法从官方数据统一更新 |
| 在 suburb 上直接存可送和运费 | 一个城市有上百个 suburb，逐个设置维护量很大；没有「区」这一层，无法整片调整，以后的阶梯运费也没有地方挂；而且字典会变成可写数据，不能再从官方数据整体更新 |

## 后果

**好处**

- 地址可以按 suburb、邮编、州精确匹配，不再依赖名称猜测。
- 字典与运营设置分离：字典可以从官方数据重新导入，不影响店铺的设置。
- 店员按大区整片设置可送和运费，个别 suburb 再单独覆盖，维护量小。

**代价**

- **与 PRD 第 10 节不一致。** PRD 按「区」勾选可送、全店一个线下配送费；现在改为配送大区加成员覆盖，运费也可以按大区设置。PRD 中「区」的验收用例（如「把帕拉马塔勾上之后可以下单」）改为对应的大区或 suburb 设置可送。以本记录和字段清单为准。
- **小程序的地址改为直接匹配 suburb。** `docs/prd/mini-prd.md` 中「取回的城市对不上则 `PLACE_OUTSIDE`」（第 191 行）、「suburb 对到区表、记下区 id」（第 192 行）和 `districts` 表（第 555 行）的做法不再适用：地址按 `name + postcode + state` 匹配字典中的 suburb，再通过大区成员判断属于哪个城市，并得到线下的可送和运费。小程序契约和 PRD 需要在小程序阶段同步调整。
- **快递城市也要录入配送大区。** 快递城市没有大区时，所有地址都会越界。例如堪培拉需要建一个大区，把 ACT 的 suburb 加进去。W-06 最好提供按邮编或按州批量加入 suburb 的功能，减少录入量。
- **suburb 字典需要初始化数据。** 要选定一份官方数据源，写导入脚本，并决定以后如何更新。在此之前，前端模拟数据中先放少量示例 suburb。
- **A 负责的订单和概览字段需要改名。** 订单地址快照 `AddressSnapshot` 中 `districtNameZh` 改为 `zoneNameZh`，并增加 `suburb` 和 `state`；概览 `CityOverview` 中 `deliverableDistrictNamesZh` 改为 `deliverableZoneNamesZh`。这次只修改了字段清单，`docs/api/admin.openapi.yaml` 中 A 区块的对应字段需要另开任务修改，在此之前两者暂时不一致。
- 城市的 `state` 创建后不能修改。确实建错了州时，只能新增一个城市。
