# 0001. 前后端分离，每端独立成工程

- 状态：已采纳
- 日期：2026-11-01
- 决策人：@MoonLight-QAQ

## 背景

拾澳有三个端：管理后台、微信小程序、未来的 APP。每个端都有前端和后端。团队目前只有 3 个人，代码放在一个仓库里，但预期业务壮大后，需要把各端拆成独立的仓库或独立的服务，分别部署和维护。

如果一开始把各端的代码混在一起，比如共用一个后端模块、共用一个前端依赖空间、共用一套业务代码，以后拆分时就要逐个文件判断归属、解开相互引用，成本很高。

## 决策

1. **最外层按前后端分离**：`../../frontend` 和 `backend/`。
2. **每一端都是一个完整的独立工程**：

   | 前端 | 后端 |
   | --- | --- |
   | `../../frontend/web`（管理后台） | `../../backend/admin` |
   | `../../frontend/mini`（小程序） | `../../backend/mini` |
   | `../../frontend/app`（APP） | `../../backend/app` |

3. 每个工程有自己的依赖文件和锁文件、配置、构建方式和部署单元。
4. **工程之间不共享任何代码，不互相引用**，包括不设立公共代码库。
5. 后端工程内部采用 controller → service → dao 的分层。
6. 工程之间只通过**接口契约**和**数据库**发生关系。

## 考虑过的其他方案

| 方案 | 没有采用的原因 |
| --- | --- |
| 后端一个 Go 模块、多个可执行程序，共享业务层 | 各端的代码在同一个模块中，拆分时要逐个解开依赖 |
| 后端各端独立，但共享一个公共规则库 | 公共库会成为所有工程的共同依赖，修改它会同时影响所有端，依然是耦合 |
| 前端用 pnpm workspace，共享组件和工具包 | 同上，共享包把各个前端绑在一起 |
| 按端划分最外层（`admin/`、`mini/` 下各有前后端） | 前后端的技术栈、工具链、负责人不同，按前后端分离更清晰 |

## 后果

**好处**

- 任何一个工程都可以直接拆成独立仓库，用 `git filter-repo --subdirectory-filter` 还能保留它的提交历史。
- 各端可以独立部署、独立扩容。例如管理端后端可以只部署在内网。
- 修改一个端，不会意外影响其他端。
- 每个工程的规则文件（`../../AGENTS.md`）只描述这个工程，AI 的上下文更干净。

**代价**

- **相同的代码要写多份。** 例如金额格式化、手机号校验，各个工程各写一份。
- **相同的业务规则也要实现多份。** 订单状态、库存锁定、退款规则，会同时出现在管理端后端和小程序后端中。为此要求：规则只在 PRD 和 `../design` 中定义一次；两边都按 PRD 逐条编写测试；修改规则时两边同时修改。
- **数据库仍然是共用的**，这是工程之间剩下的耦合。表的写入归属在表设计阶段明确。真正拆分数据库，要等到各端拆成独立服务时再做。
