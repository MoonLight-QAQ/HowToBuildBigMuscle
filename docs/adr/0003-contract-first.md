# 0003. 契约先行，前端用模拟数据开发

- 状态：已采纳
- 日期：2026-11-01
- 决策人：@MoonLight-QAQ

## 背景

开发顺序是：管理后台前端 → 表设计 → 小程序前端 → 后端。前端开发时，后端还不存在。

如果前端凭自己的理解假设接口的样子，等后端做出来时，双方对字段名、数据格式、错误处理的理解很可能对不上，导致大量返工。同时，团队使用 AI 编码，AI 会按「最常见的写法」自行发明接口格式，如果没有明确的约定，每个人的 AI 写出来的接口风格都会不同。

## 决策

1. **每个端有一份接口契约**，使用 OpenAPI 3.1 编写，放在 `../api`，如 `admin.openapi.yaml`。契约是前后端之间 **唯一**的约定。
2. **接口通用约定**写在 `../api/conventions.md`， **业务字段**写在 `docs/design/` 下的字段清单，契约以这两份为准。
3. **先写契约，再写代码。** 需要新接口或新字段时，先改契约，再改前端和后端。
4. **前端的接口类型从契约自动生成**（openapi-typescript），不手写。
5. **前端用按契约编写的模拟数据开发**：
   - 管理后台用 MSW，在浏览器中拦截请求。
   - 小程序不支持 Service Worker，改为在请求封装层按环境变量切换为本地模拟数据。
   - 模拟数据必须使用生成的类型，并模拟真实的业务规则和错误码。
6. 后端完成后，前端关闭模拟数据，直接对接真实接口。页面代码不应因此修改。

## 考虑过的其他方案

| 方案 | 没有采用的原因 |
| --- | --- |
| 先做后端，再做前端 | 与团队确定的开发顺序不符；前端要等很久才能开始 |
| 前端在页面里直接写假数据 | 假数据分散在各个页面，对接后端时要逐个删改；格式没有约束，对接时问题集中暴露 |
| 前后端共享手写的 TypeScript 类型 | 后端用 Go，无法直接使用；而且违反了工程之间不共享代码的原则（见 0001） |

## 后果

**好处**

- 前端和后端可以并行开发，对接时只需关闭模拟数据。
- 契约一改，前端重新生成类型，类型检查就能指出哪里需要同步修改。
- 所有人和所有 AI 都按同一份契约写代码，接口风格一致。
- 模拟接口实现了业务规则和错误码，前端能在没有后端时完整开发出错误提示和边界情况。

**代价**

- 开发页面之前，要先投入时间写契约。
- 修改契约会影响其他成员和后端，需要提前沟通，并在 PR 中单独列出。
- 模拟接口需要维护：契约变化时，模拟数据也要同步修改。
- 后端开发时，需要严格按契约实现，不能按自己的习惯调整接口格式。
